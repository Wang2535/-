# 新一代开发方案 — 纵向切片增量交付

> 基于诊断报告的核心发现：分组开发产生大量孤立模块，但集成永远落后于开发。  
> 本方案的核心原则：每个任务从数据层→引擎层→UI层→浏览器验证 完整打通。

---

## 一、开发模式转变

### 从"横向分模块"到"纵向切片"

```
旧模式（横向）:                    新模式（纵向）:
                                    
数据层 ────────────────▶           切片1: 数据→引擎→UI→验证  ✅ 可玩
                  │                 
引擎层 ────────────────▶           切片2: 数据→引擎→UI→验证  ✅ 可玩
                  │                 
UI层 ──────────────────▶           切片3: 数据→引擎→UI→验证  ✅ 可玩
                  │                 
集成 ────────────────▶             切片4: 数据→引擎→UI→验证  ✅ 可玩
```

### 新开发原则

1. **每步可验证**：每个任务完成后，必须能在浏览器中看到效果
2. **每阶段可玩**：每个阶段结束，游戏至少有一个可玩的循环
3. **小步快跑**：每个任务控制在1-2小时工作量，不跨层
4. **Prompt精简**：每个Prompt不超过500行，只包含当前任务所需的信息
5. **单一数据源**：每阶段确定一套数据格式，淘汰旧格式

---

## 二、三阶段路线图

### 阶段一：骨架打通（最小可玩循环）

**目标**：玩家能在L1地图上掷骰子→移动→触发格子→进入战斗→战斗胜利→返回地图  
**验收标准**：打开浏览器，完成一次完整的"投骰子→走格子→打关卡→拿奖励"流程  
**预计任务数**：5个  

| 任务 | 内容 | 复用代码 | 新建代码 | 验收 |
|------|------|---------|---------|------|
| S1-T1 | 统一数据源+渲染L1地图 | PerLayerTopologyGenerator(改造) | 数据格式适配器+L1专用渲染器 | 浏览器中可见L1葫芦形地图，20个格子位置正确，路径连接可见 |
| S1-T2 | 骰子+移动系统 | MovementEngine(简化) | 骰子UI组件+曲线移动动画 | 点击"投骰子"→随机1-6→棋子沿路径平滑移动→停在目标格 |
| S1-T3 | 格子触发+事件反馈 | CellStateMachine(简化) | 格子效果UI弹窗 | 停在关卡格→弹出"进入战斗/跳过"选项 |
| S1-T4 | 基础战斗循环 | 已有关卡模式引擎 | 爬塔模式战斗入口/出口 | 进入战斗→7阶段回合→胜利/失败→返回地图 |
| S1-T5 | 奖励+返回地图 | RewardSystem(简化) | 战斗胜利UI+资源更新 | 胜利后显示"获得2张卡牌+技术值+3"→返回地图→资源已更新 |

**阶段一结束时游戏体验**：
```
开始游戏 → 看到L1地图 → 掷骰子 → 走到关卡格 → 选择进入战斗 → 战斗胜利
→ 获得卡牌奖励 → 继续掷骰子 → 走到Boss格 → 击败Boss → 进入L2
```

## 三、每阶段Prompt设计规范

### 新Prompt模板

```
# [阶段]-[任务编号] 任务：[一句话描述]

## 背景（不超过200字）
[只包含当前任务需要的上下文，不引用完整设想]

## 当前代码状态
[列出涉及的现有文件，标注"保留/修改/废弃"]

## 任务要求
1. [具体步骤1]
2. [具体步骤2]
3. [具体步骤3]

## 验收标准
- [ ] 在浏览器中能看到...
- [ ] 点击/操作后能...
- [ ] 状态变化为...

## 数据格式
[只定义当前任务需要的数据结构，不超过50行]
```

### 与旧Prompt的对比

| 维度 | 旧Prompt | 新Prompt |
|------|---------|---------|
| 长度 | 3000-8000行 | ≤500行 |
| 上下文 | 完整设想+前N轮总结 | 仅当前任务需要的信息 |
| 代码示例 | 大量伪代码和实现细节 | 只给接口定义，实现由AI决定 |
| 验收 | 测试用例模板 | 浏览器可见的行为描述 |
| 焦点 | "实现这个模块" | "让玩家能看到/做到X" |

## 四、现有代码复用指南

### 可直接复用（无需修改）

| 模块 | 文件 | 说明 |
|------|------|------|
| 类型定义 | `types/*.ts` | 大部分类型定义正确，可直接使用 |
| 常量配置 | `constants/*.ts` | 9层配置、技能概率、区域效果配置 |
| 关卡数据库 | `data/levelPool.ts`等 | 142关数据已完备 |
| 工具函数 | `utils/*.ts` | 概率计算、随机数、验证函数 |
| 战斗引擎 | 关卡模式已有引擎 | 7阶段回合战斗系统 |
| 测试文件 | `__tests__/*.test.ts` | 单元测试可复用，E2E测试需重写 |

### 需要修改

| 模块 | 问题 | 修改方向 |
|------|------|---------|
| PerLayerTopologyGenerator | 输出格式与渲染器不匹配 | 增加适配器或直接修改输出格式 |
| GourdShapeFactory | 仅生成数据，未接入渲染 | 在阶段一S1-T1中直接接入渲染器 |
| GourdMapRenderer | 使用第九轮数据格式 | 阶段一重写为接受新格式 |
| TowerGameEngine | 代码完备但未接入UI | 阶段一接入控制器和UI |
| MechanicVisualizer | 独立组件未挂载 | 阶段二挂载到主渲染流程 |
| ZoneEffectResolver | 逻辑存在但未执行 | 阶段二接入引擎 |

### 可以废弃

| 模块 | 原因 |
|------|------|
| `L1_visualData.ts`~`L9_visualData.ts` | 被ShapeFactory+TopologyGenerator替代 |
| `gourdTopologies.ts` | 数据格式冲突，被统一数据源替代 |
| `mapTemplates.ts` | 数据格式冲突，被统一数据源替代 |
| 多套重复的CellType/ZoneType定义 | 统一到types/下的单一文件 |
| 旧的LayerMapRenderer（如果还存在） | 已被GourdMapRenderer替代 |

## 五、风险与应对

| 风险 | 可能性 | 影响 | 应对措施 |
|------|--------|------|---------|
| AI无法理解精简后的Prompt | 低 | 中 | 提供清晰的接口定义和验收标准 |
| 某个阶段卡住 | 中 | 高 | 每阶段不超过5个任务，卡住时可跳过非核心功能 |
| 现有代码接口冲突 | 高 | 中 | 阶段一就统一数据格式，避免后续冲突 |
| 浏览器渲染性能问题 | 低 | 中 | 阶段一就进行性能测试，确保基础流畅 |
| 设想变更 | 中 | 低 | 方案按优先级排列，核心功能先做 |

## 六、成功标准

阶段一完成后，你应该能：
1. 打开浏览器看到L1葫芦形地图
2. 点击"投骰子"按钮，棋子沿路径移动
3. 停在关卡格后弹出战斗选项
4. 进入战斗并胜利后获得卡牌奖励
5. 整个流程流畅无报错

**这是过去11轮都未能达到的状态。** 一旦阶段一完成，后续的每阶段都是在已有可玩基础上增加功能，而不是从零开始。
